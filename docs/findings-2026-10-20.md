# Findings 2026-10-20

- `SonioxTranslationEngine` sends `api_key` in the config message (as MTGMap does). Soniox's
  keepalive doc calls that the legacy path ("Migrate WebSocket authentication"); moving to the
  newer auth is still to do
- MTGMap's `SystemAudioCaptureSource` (the source of Kanpe's copy) still runs the tap
  teardown/rebuild and watchdog on the main queue, so it likely has the same UI freeze
- Without headphones the mic also picks up the remote voice from the speakers, so it gets
  transcribed twice (as 相手 and 自分); echo cancellation (voice processing IO) would fix it
- AAC with an input device of more than 2 channels is untested; `AudioFileRecorder` logs and
  skips if the file can't be opened
- Late translation tokens can land on the next line when the same speaker keeps talking
  (seen 2026-10-20: the 訳 of "You—" was prefixed to the next line). Matching by Soniox token
  timestamps (`start_ms`) instead of arrival order would fix it
- Re-transcribing the saved m4a with `stt-async-v5` after the meeting could give a cleaner record — Soniox
  says async diarization is "significantly" more accurate than real-time, so this is also the fix
  for speakers split in two (seen 2026-10-21 in an in-person meeting)
- STT provider check (2026-10-21): on Artificial Analysis' streaming leaderboard (English-heavy) Soniox v5
  ranks ~14th on WER (4.50%) but first on latency and near-cheapest; it is the only one with translation
  in the same stream. No independent Japanese benchmark found. If accuracy becomes the issue, run
  soniox/soniox-compare (MIT) on saved meeting audio against ElevenLabs Scribe v2 RT, Gemini 3.5
  Transcribe Live, and Qwen3 ASR Flash
